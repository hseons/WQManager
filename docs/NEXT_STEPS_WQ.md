# WQManager 下一步：围绕 worse_query 的能力拓展

日期：2026-11-15。本文是下一轮的研究与实施顺序，不代表已实现或已经真机验证。

2026-11-18 更新：0.5.0 已完成全局文件搜索、空间变化窗口与合计趋势、
文件审计/导出中心以及重复清理安全约束；下列研究项仍未开始或仍待真机验收。

## 当前迭代的基础

0.4.0 补上空间变化、文件查找、串行批量备份、备份备注与保护、备份浏览与对比、目录级自定义备份。
P3「密码加密导出」按用户决定取消，不纳入下面的排期。

接下来的目标是把 WQ 已经取得的容器访问能力做成有实际用途、结果可解释的工具。
当前 WQManager 的产品操作范围仍是已识别 App 的数据容器。

## 已确认的信息与待验证的信息

参考来源固定在以下修订，避免把不断变化的上游描述当成自己的验证结果：

- [worse_query README](https://github.com/forcequitOS/worse_query/blob/d1540e20cd82b974d891e0551ced6d6aeb570ac2/README.md)。
  上游列出 App Data、App Groups、PluginKitPlugin、InternalDaemon 等容器；
  System Data、SystemGroup 以及 App Groups 父目录的可达性有系统版本限制。
- [WQFiles README](https://github.com/kolbicz/WQFiles/blob/bb81069401875a470a032830b8e6bc934fbd9146/README.md)。
  上游已经探索共享容器、扩展数据、结构化文件查看等方向，可以参考产品边界和失败场景。
- 本项目 `WQAccess.h/.m`、`WQLaunchServices.h/.m`：已有 scoped token、容器身份、
  文件操作及枚举基础，但本轮没有新增其他容器类别的访问或写入入口。

上游声称可访问某类路径，不等于每个容器都能读取，更不等于可安全写入。
父目录可枚举、单个容器可打开、内容可读、内容可写，需要分开记录。
系统版本号也不足以证明兼容性，还需记录系统 build、设备、签名方式和 App Group 状态。

## 第一项：WQ 能力与兼容性诊断

2026-11-16 实施状态：首版已实现于 0.4（构建 14，发布修订 0.4.2）。
入口为设置 →「访问能力」，检查范围先限定为索引中用户选择的一个 App 数据容器。
提供签名证据、系统 build、token 失败阶段、容器身份、目录和有限文件读取样本、
可取消检查与主动导出的脱敏 JSON 报告。其他容器类别和写入能力明确标记未验证。
不推断签名工具或证书品牌，也不把 EACCES 直接等同于数据保护。
真机签名／权限场景的兼容性验收仍待执行，首版完成不代表下面的开放条件已通过。

**真实问题**：用户看到「受限」时，很难判断是签名缺 App Group、token 获取失败、
容器身份缺失、文件保护，还是系统行为变化。

**MVP**：设置中增加「访问能力」页面，按容器类别显示已观察到的能力和失败原因。

1. 记录设备与系统 build、App Group 是否存在、已有访问方式和最近一次错误类别。
2. 分别表示「已发现容器」「能打开目录」「能读取内容」；不靠一个总开关推断所有权限。
3. 先使用已知目标的只读探测，不在启动时扫描整个 inode 范围。
4. 写能力只根据用户实际执行的正常操作记录；不通过创建、删除其他 App 文件探测权限。
5. 提供用户主动导出的脱敏报告，去除 token、文件内容和完整用户文件路径。

**验收**：至少验证一个受支持真机 build 的正常签名、缺少 App Group、拒绝访问、
受限文件、容器变更场景。失败要落入明确类别；模拟器结果标记为 UI/服务验证。

**建议级别**：Validate first。它是其他容器功能可靠开放的前置条件。

## 第二项：App Groups 与扩展容器的只读总览

**真实问题**：主 App 容器只包含一部分数据。共享数据库、附件或扩展数据可能放在其他容器，
用户容易把当前备份理解成整个 App 的全部状态。

**MVP**：先展示关联容器、占用、关联来源；支持只读浏览和用户选择的导出。

1. 检查本项目现有 LaunchServices 查询是否能可靠提供 App → 扩展 → App Group 关系。
2. 使用 Bundle ID、扩展 ID、Group ID 作为身份；UUID 路径只作为本次操作的解析结果。
3. 区分已验证关联、多个 App 共用、关联未知三种状态，不按名称相似度猜归属。
4. 仅为已识别且当前可读的容器提供浏览/导出，复用文件索引、预览和操作互斥。
5. 一个共享容器可以属于多个 App，空间总览按容器身份去重。

**主要成本**：归属识别、共享数据去重、不同系统版本的发现方式、读取一致性。

**验收**：覆盖一个带扩展的 App、一个多个 App 共用的 Group、一个访问受限的 Group；
界面能解释来源和范围，重复关联不重复统计。

**开放条件**：第一项诊断在真机上通过，且关联关系有可重复的读取证据。

共享容器的写入与恢复单独评估：需要知道所有写入者是否关闭，设计多容器一致性、
安全备份与独立回滚日志。先验证只读价值，再决定是否进入该阶段。

## 第三项：结构化数据检查台

2026-11-16 实施状态：只读 MVP 已实现于 0.4（构建 15，发布修订 0.4.3）。
支持二进制/XML plist 树、SQLite 普通表结构、100 行分页与所选表 CSV 导出。
SQLite 仅打开工具工作副本，复制主文件与 WAL 前后检查身份、大小及修改时间；
变化文件、活动恢复日志、链接和超限输入会停止处理。该检查是尽力的一致性判断，
仍要求用户先关闭来源 App，不将它称为并发写入下的原子快照。
已覆盖 WAL、损坏数据、大字段、导出上限与取消的本地测试，以及模拟器分页/分享 UI。
真实容器、文件保护与真机后台中断验收仍待执行，详见 `RELEASE_0.4.3.md`。

**真实问题**：目前能看到文件大小，但数据库和二进制 plist 仍不便理解。

**MVP**：增加只读 plist 树与 SQLite 表浏览，帮助解释数据和占用。

- plist：识别二进制/XML，按类型展开字典与数组，对大字段折叠并限制深度。
- SQLite：在工具自己的工作副本上查看结构、分页读取表、导出所选表。
- SQLite 工作副本必须处理 WAL 一致性；先关闭源 App，再复制数据库及必要日志并验证。
  在这个条件得到验证前，不把一次普通文件复制称为一致的数据库快照。
- 加密或应用自定义格式显示「格式未识别」，不把文件访问权限等同于解密能力。
- 导出由用户选择具体表/文件，不自动汇总账号、聊天内容或其他个人数据。

**验收**：大数据库内存有界；主线程不扫描全表；分页与取消有效；
二进制 plist、大字段、损坏数据库、WAL 场景有可复现样本。

**建议级别**：Build MVP，但只读；对源 App 的编辑和数据库写回另行论证。

## 第四项：目录变化定位实验

**真实问题**：当前空间历史能回答「哪个 App 变大」，还缺少「哪个目录变大」。

**MVP**：用户主动保存单个 App 的目录快照，下一次扫描比较目录体积和文件增减，
从增长榜跳到对应文件列表或空间透镜。

- 默认只保存相对路径和元数据，不保存文件内容；给出条目上限和保留数量。
- 有权限缺失、扫描中断或容器身份变化时，不生成完整变化结论。
- 允许用户在使用 App 前后主动采样，用实际变化判断离线资源、附件和缓存的位置。
- 「增长很多」只作为定位线索，不直接转成删除规则。

**开放条件**：先收集 0.4.0 增长榜的实际反馈，确认用户确实经常需要进一步定位。

## 实施顺序与决策门槛

1. 先完成 0.4.0 的真机回归：嵌套目录备份/恢复、失败回滚、大容器、后台中断、
   token 失效与应用更新后的容器身份变化。
2. 增加访问能力诊断，形成设备/build/签名方式的兼容性记录。
3. 验证 App Group 和扩展归属，再推出只读总览与选择性导出。
4. 结构化文件首版已实现，继续真机验收；根据实际反馈决定是否做目录变化实验。

研究结果应包含：测试设备与 build、签名方式、输入容器身份、实际可读范围、
失败原因、耗时和可复现步骤。只有可重复验证的能力才进入产品开关。

本计划不承诺固定日期，也不把上游列出的所有路径直接变成通用写入入口。
